# Changelog

Notable user-visible and operational changes, newest first.

## Unreleased

- **Review work can be assigned.** A team dividing a few hundred requirements had no way to say who reviews what. Requirements and stories have an **Assignee** (a picker of the named accounts in the drawer, or free text — a name or a team — on installations without accounts; a person must exist and be active, and an assignment is recorded in the audit trail with the old and new value like any other edit). The tables show "→ name", each list has an **Assigned to** filter (all, assigned to me, unassigned, or a person), the assignee is in the CSV and Excel exports and in both imports (columns `Assignee` or `Owner`; a name that is not an account refuses the whole file, with its line), and the API takes `assignee` on create and update. Tests: `tests/test_assignee.py`, `tests/ui/assignee.py`.
- A **Copy link** button in the requirement and story drawers puts the item's own address on the clipboard (falling back to the legacy copy command on plain-HTTP installs), now that an address can open the item; a key that does not exist (a mistyped or deleted item) just shows the tab. Extends `tests/ui/deep_links.py`.
- **Requirements and stories can be linked to.** A search result took you to the project's tab and left you to find the item; the audit trail named items you could not open. An address ending in an item's key (`#/p/<project>/requirements/REQ-002`, `.../stories/US-001`) now opens that item's review drawer; the keys in search results and in the audit trail (Audit tab and Overview) are links to it, so an item can be pasted into chat or a ticket. The address returns to the tab once the drawer is open, so closing it or saving does not reopen it. Browser test: `tests/ui/deep_links.py`.
- **A safe way to switch `ORIGIN_SECRET` on.** Enforcing it before the proxy rule exists makes the site refuse everybody. `ORIGIN_SECRET_REPORT_ONLY=1` counts what would be refused (`fabulist_origin_refused_total{mode="report"}`) and refuses nothing: set it with the secret, add the Cloudflare rule, watch the counter stop growing for normal traffic, then remove it to enforce (`mode="enforced"`). Test in `tests/test_origin_secret.py`.
- Found by probing the reference cluster's ingress (a throwaway `traefik/whoami` behind Traefik 3.6, deleted afterwards): a request from outside reaches the ingress with a private source address (`172.25.x.x`), not the caller's own, because of address translation in front of the node. So an ingress allow-list of Cloudflare's address ranges would refuse every request, Cloudflare's included, on this cluster; the README now says to check this first and points to `ORIGIN_SECRET`, which does not depend on source addresses, as the option that works here. Also meant: behind that translation `X-Forwarded-For` carries the same private address for everyone, which is why `TRUST_CF_CONNECTING_IP` stays on (the default) while the site is behind Cloudflare.
- A cross-browser check (`tests/ui/cross_browser.py`): the project list, requirements table, review drawer, overview, admin overview, dark theme and API reference in Firefox and WebKit (Safari's engine) as well as Chromium, with no script or console errors. It passed on the first run in both.
- Tests for how the tracker clients behave when a tracker misbehaves (`tests/test_tracker_requests.py`): a rate limit or server error is retried with a back-off (1.5 s, then 3 s) up to three attempts, network trouble is retried and then named, a refusal (4xx) is final with the tracker's own message (Jira's `errorMessages` and `errors` included), an empty success is accepted, and every shape of error body reads sensibly. These were the main untested branches of the tracker clients.
- Measured test coverage for the first time: 96% of the application's lines (4,611 lines, 199 not run by any test), with `coverage.py` run on the cluster for the measurement only (not a project dependency). The largest untested piece it found was the Anthropic provider (the request it sends, joining the answer, listing models, the connection test, its error messages), which is now covered by `tests/test_anthropic_provider.py` with a simulated Messages API. Other remaining gaps are error branches of the tracker clients and the background loops' exception handlers.
- **A remote embeddings provider is retried and its failures are visible.** The calls to an OpenAI-compatible `/embeddings` endpoint had no retry (one 503 and the document was stored without search passages, with only a line in the server log) and no tests at all. Each batch of 64 texts is now tried up to three times with a back-off when the provider hiccups (network error, 429, 5xx); a refusal (4xx) is explained ("check the model name and the key"); and when indexing finally fails, the upload answers `index_error` and the page says the document is stored but not searchable yet and that the index can be rebuilt once the provider works. New tests with a simulated provider (`tests/test_remote_embeddings.py`) cover the model and batches sent, answers arriving out of order, retries, giving up, a wrong vector size and a missing model.
- The API reference follows the light/dark choice in its one hand-written colour too (the red of required-field markers ignored an explicit choice on a system set the other way). A test pins both selectors.
- The README's deploy section lists what `deploy.sh` actually does, in order (clean-main guard, secrets, image build and scan, waiting for runs, the limited database role, zero-downtime rollout, monitoring, the live smoke test), and a test checks the script still contains each piece the README claims.
- **Evaluate scores story writing as well.** After extraction, the same trial now writes stories for the sample's twelve requirements (taken from the BRD itself, so the provider does not write its own exam) and reports how many of the twelve the stories cover, which are not covered, how many stories have Given/When/Then criteria, and the cost: "Stories: 6 stories cover 11 of 12 requirements (not covered: REQ-010); 6 of them have Given/When/Then criteria; 3 requests, 2.1 s." The button runs both stages; through the API it is `?stages=requirements,stories` (default: requirements only, since stories cost a second round of requests). Tests in `tests/test_provider_evaluation.py` include a weak simulated writer that covers one requirement per area with non-Gherkin criteria.
- The README opens with a contents line linking every section and the other documents (architecture, acceptance, changelog, security policy); a test checks every link leads to a real heading or file.
- A webhook that is subscribed to finished runs says so on the Integrations page (a "Run notifications" badge), instead of that only being visible by opening it. Found in a screenshot of the new last-delivery line.
- **A webhook shows how its last delivery went.** A failing receiver was only visible in the server logs. Each webhook integration now remembers its latest delivery (a backlog push, a run-finished notification, or the test ping): which event, when, whether it worked, and the reason if not. It is on the Integrations page ("Last delivery (run.finished): failed: ConnectError … · 3 min ago") and in `last_delivery` of `GET /api/integrations`. Tests in `tests/test_run_notifications.py`.
- **Score an AI provider before relying on it.** The only check was "does it answer" (Test). **Evaluate** on Admin > AI providers (`POST /api/admin/providers/{id}/evaluate`) runs the built-in sample BRD, whose answer is known (twelve numbered requirements, one an open item that must stay open), through that provider and reports how many of the twelve numbers it found and which it missed, whether the TBD survived or was "resolved", and what it cost in requests, tokens and time, in one sentence ("Found 12 of 12 requirement numbers; kept the open item (TBD) as it was; 2 requests, 1.3 s."). An unreachable provider says so instead of failing. Administrators only, recorded in the administrative trail. It is a quick trial on one small document, not a benchmark: compare two providers on a sample of your own BRDs before choosing. Tests: `tests/test_provider_evaluation.py` (including a weaker simulated model that scores lower and loses the TBD), `tests/ui/provider_evaluate.py`.
- The capacity table in the README is refreshed from the latest full load runs (the large-upload memory peak is 580-640 MiB, not 460; search across 50,600 requirements takes under 0.1 s; the home list with the activity column answers in about 20 ms with 300 projects; an earlier line here said 0.23 s, a figure from a full multi-scenario run under load, measured again on its own).
- **Projects say when they were last worked on.** The project list showed only when each was created, which tells a long list nothing about what people are doing now. Each project has a `last_activity` (the latest entry in its audit trail, else its creation), the cards say "Active 3 min ago · created 2 weeks ago", and the list can be sorted by **Recently active**. Tests: `tests/test_project_activity.py`; the sort is covered in `tests/ui/home_list.py`.
- README and acceptance page mention the account lifecycle (change your own password, temporary passwords, last activity).
- **A password an administrator chose can be made temporary.** The administrator knows it, so the person should replace it. Adding a user or resetting a password has a checkbox (ticked by default; `must_change` in the API, off by default there): until the person sets their own on the Account page, every request except the password change, their identity and the page's metadata is answered `403` (`password_change_required`), however they sign in, and the page takes them straight to a "Choose your own password" form. Named administrators are held to it too; the bootstrap login has no account and is not. The Users table flags accounts with a change pending, and the user-created entry in the administrative trail says so. Tests: `tests/test_must_change_password.py`, `tests/ui/force_password_change.py`.
- **"Last active" on the Users page.** Access reviews ask who still uses their access and who never did, and nothing said. Each named account's last use of the API (password, token or single sign-on session; not the page's own files) is recorded about once every quarter of an hour (not on every request: that would turn every read into a write) and shown in a Last active column ("never" for an account nobody has used); `last_seen` is in `GET /api/admin/users`. Tests: `tests/test_last_active.py`.
- **People can change their own password.** Only an administrator could set a named account's password. The Account page has a Password card (current, new, repeated; at least 12 characters) and there is `POST /api/me/password`, for any role, viewers included: it checks the current password, refuses a weak or unchanged one, works at once (the old password stops working; the browser asks to sign in again), and records "password changed" in the administrative trail without any password. Not available to the bootstrap login (set in the deployment), to a bearer token (a leaked token must not be able to take the account over) or on the page for single-sign-on sessions. Tests: `tests/test_change_password.py`, `tests/ui/change_password.py`.
- Architecture and acceptance pages mention the weekly test restore and the backup retention.
- **Backup retention is 7 days plus five Sundays.** The nightly job kept the last 7 dumps and nothing older, so a problem noticed after a week-and-a-half had no backup from before it. It now keeps every dump of the last 7 days and the Sunday dump of each of the last 5 weeks (35 days); the logic is `scripts/backup-prune-job.sh`, tested in the restore drill with a dump for each of the last 61 days (it must keep exactly the last 8 days and the Sundays up to 35 days). Both job scripts now come from one ConfigMap, `fabulist-job-scripts`.
- **The backups are test-restored every week, in production.** A CronJob (Sundays 04:30, `deploy/k8s/restore-check.yaml`, script `scripts/restore-check-job.sh`) restores the newest nightly dump into a scratch Postgres inside the job, with the volume mounted read-only and no knowledge of the real database, and checks that it is recent (under two days), restores with no error, has the tables, and has the append-only triggers; a failed job raises the critical alert `FabulistRestoreCheckFailed` (runbook row included). The same script runs as the last step of the restore drill, which found something on its first run: a restore into a server without the production roles fails on the ownership statements, so the check restores with `--no-owner --no-privileges` (the real restore, into the real database, still uses the documented command).
- The database's size is a metric (`fabulist_database_size_bytes`) with an alert, `FabulistDatabaseLarge` (over 3.5 GB for an hour; the Postgres volume is 5 GiB, and the 5 GiB backups volume holding seven dumps fills first), with a runbook row on what to expand or remove. (Kubernetes' own volume-usage metrics are not collected on this cluster, so an alert on those would never have fired: checked in Prometheus.)
- The two newer refusal signals are watched: alerts `FabulistRateLimiting` (over 100 requests refused for the per-person limit in 10 minutes) and `FabulistOriginRefusals` (over 20 requests without the origin secret), each with its runbook row, and a dashboard panel graphing both counters. The existing tests check that the metrics exist and the panels do not overlap, and that every alert has a runbook row.
- **The product taxonomy can be emptied, and stays empty.** Every restart re-seeded the built-in medical-distribution classes whenever the table was empty, so an administrator who removed them (for another industry, or for none) got them back at the next deploy. Seeding now happens once (marked in the settings table; existing installs count as seeded). **Start from scratch** on the Product taxonomy page (`DELETE /api/admin/taxonomy`, with a confirmation, recorded in the administrative trail) removes every class and attribute rule. Tests in `tests/test_admin_audit.py`.
- README introduction says what is configurable for other industries (the business domain and the product taxonomy), instead of reading as medical-only.

Admin > Generation settings has a **Business domain** field (default unchanged: medical product distribution; one line, up to 120 characters; empty goes back to the default) and both the extraction and the story instructions use it. Product taxonomy and platform profiles are separate and unchanged. Tests: `tests/test_business_domain.py`, `tests/ui/business_domain.py`.
- `docs/ACCEPTANCE.md`: nineteen acceptance scenarios a business owner or security reviewer can walk through before rollout, each with the automated test that proves it on every change, and an honest list of what the checks do not cover (real AI quality, more than one replica, real devices). A test fails if a named test or script does not exist.

Statuses other than `draft`, `approved` and `rejected` come in as drafts, counted as `statuses_not_recognised` in the answer and mentioned in the notice. (Requirement import stays strict.)
- **Import stories from CSV or Excel**, the counterpart of the requirement import, for moving a backlog in from a Jira export or another Fabulist: **Import file** on the Stories tab (also from the empty state), `POST /api/projects/{id}/stories/import` (CSV text) and `.../stories/import-file` (an uploaded .csv or .xlsx; the sheet called Stories, else the first). Same care as the requirement import: validated first (nothing imported if a row is wrong), a title already in the project is skipped, numbering continues, one audit entry per story plus an "imported" entry. Tests: `tests/test_stories_import.py`, `tests/ui/stories_import.py`.
