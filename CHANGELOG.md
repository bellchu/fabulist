# Changelog

Notable user-visible and operational changes, newest first.

## Unreleased

- **A working API reference.** FastAPI's built-in `/docs` and `/redoc` loaded their scripts and styles from a public CDN, which the Content Security Policy blocks (so they rendered blank) and which a locked-down corporate network would not reach. `/docs` is now a self-contained page served by the app: introduction (authentication with tokens or Basic credentials, the `X-Requested-With` header, errors, runs and queues), the operations in 13 groups, a filter, and for each operation its parameters, request-body fields with the allowed values, and responses. The OpenAPI document behind it now groups every operation (the URL decides the group) and documents the choice fields (`documents`, `stories_for`, `scope`, `visibility`) with their values. The Account page links to it. Tests: `tests/test_api_reference.py`, and `tests/ui/api_reference.py`, which runs with the policy enforced and includes an accessibility scan.
- A running AI run now shows how far along it is: a real progress bar and "5 of 14 done · about 11 s left" (the pace so far, from the start time the server records when a worker begins the run, so it survives a reload) instead of an endless animation and a section name. Works for requirement extraction and story generation; the old animation shows only until the first section is done. Browser test `tests/ui/run_progress.py` (with an accessibility scan).
- Operators can see when an AI provider is throttling: new counter `fabulist_llm_retries_total{reason}` (`rate_limited`, `server_error`, `unreachable`), a Grafana panel "AI provider retries by reason", and the alert `FabulistAIProviderThrottling` (more than 100 rate-limit or server-error retries in 15 minutes for 10 minutes). Since patient retries hide throttling from users, this is where it shows.
- **Runs survive a flaky AI provider.** The new `flakyai` load scenario (a provider that fails 25% of requests with rate limits, server errors and non-JSON replies) failed 2 of 6 runs of 46 sections, and a real run of hundreds of sections would almost never have finished: a request got three quick attempts (about 4.5 s of waiting), the provider's `Retry-After` was ignored, and a non-JSON reply was asked for again only once. Now a request gets up to `LLM_MAX_ATTEMPTS` (default 6) tries, waiting what the provider asked (`Retry-After`, up to a minute) or 1.5 s doubling with jitter; a rate limit pauses every call to that provider across all sections and runs, so parallel sections do not hammer it; and a reply that is not a JSON array is asked for again twice. Quota exhaustion (429 with a quota message) is still not retried, and a cancel is still noticed within a quarter of a second.
- Docs: a "Capacity and sizing" section in the README with the measured load-test results and what to turn when it is not enough, the missing settings (`MAX_CONCURRENT_PARSES`, `PARSE_WAIT_SECONDS`, `LLM_TIMEOUT_SECONDS`, `MALLOC_ARENA_MAX`), and a test that fails when a setting in the code is not documented.
- **Private projects.** Every signed-in person used to see every project, which does not work when teams' BRDs are confidential. A project can now be private to chosen people (Edit > Who can see this project, or when creating it): only they and administrators can see it, open anything in it or find it by search; everyone else gets "not found". Chosen people keep their own role (a viewer stays read-only), the person making the change always stays in, and changes are in the audit trail. Enforced by one guard on every route that names a project (`project_guards`, which also does the archived read-only check), so routes added later are covered; the project list is filtered the same way and shows a Private badge. Without named accounts nothing changes. API: `visibility` on create, `GET/PUT /api/projects/{id}/access`, `GET /api/people`. Tests: `tests/test_project_access.py` (every route group, role combinations, validation) and `tests/ui/project_access.py` (two accounts).
- Load scenario `manyprojects` (`scripts/load-test-k8s.sh manyprojects`): 300 projects with BRDs and requirements. The home list, project summary, metrics scrape and admin overview each answer in about 10 ms, so a company-wide installation needs no change; the scenario guards that.
- **Stories for new requirements only.** "Regenerate" replaced every story, including edited, approved and tracker-linked ones, so there was no safe way to cover requirements added later. The stories run panel now offers **Requirements without stories**: it writes stories only for requirements no story covers (as many feature-area groups as fit 'Max sections per run'; a big backlog takes a few runs), adds them after the existing stories, and leaves those untouched (numbering continues, and a new story never takes an existing story's title). **All requirements: start over** is still there, with its warning, and works in batches too (the first batch replaces the stories when it is saved, so a failed run changes nothing; the rest then have no story). API: `stories_for` = `uncovered`, `reset` or `all` on `POST /runs` and `GET /runs/estimate`; the project summary reports `requirements_uncovered`. Queued runs of this kind also survive a restart. Browser test: `tests/ui/incremental_stories.py`.
- The Sources tab draws the document list a page at a time too (300, then "Show more"), so a project with a thousand BRDs does not build a thousand rows with their buttons on every visit. Covered in `tests/ui/paged_tables.py`.
- Grafana dashboard: a new "Capacity" row graphs AI runs running vs waiting in the queue, and the app's memory (resident, peak, limit), the signals behind the `FabulistRunQueueBacklog` and `FabulistMemoryNearLimit` alerts. A test checks the dashboard JSON is valid, that these panels exist with the right metrics and that no panels overlap.
- `deploy.sh` no longer silently kills AI runs that are executing (the wait is `scripts/wait-for-runs.sh`, tested with a stub `kubectl`): before replacing the server it waits (up to `DEPLOY_WAIT_FOR_RUNS` minutes, default 15; `0` skips) for them to finish, and warns if any are still running. Together with queued runs surviving a restart, a deploy now only interrupts a run that outlasts the wait.
- Queued runs survive a restart or deploy. They used to fail with "start it again" whenever the server restarted; a run that is only waiting has done no work, so the new server now starts it again, in its place in line. Each run records how to start it (provider, scope, which BRDs), and exactly one server can claim and execute a run, so a rolling deploy (two servers briefly) cannot run it twice. Runs that were already executing at the time are still failed with a clear message, since resuming them would redo the work and the AI cost.
- Accessibility checks now also cover the newest screens, in light and dark: the run panel with its "BRDs to read" choice, the New badges on the Sources tab, the "Show more" row of a long table, and the queued-run state. All pass (no serious or critical WCAG A/AA violations).
- **Large uploads no longer take the server down.** The load test (`bigfiles`: 20 requesters upload a 6 MB Word file at the same moment) killed the pod out of memory three times over, and a single 6 MB `.docx` took 36 s of CPU to read. Fixed in layers, each verified: python-docx looked every paragraph's style up from scratch (0.8 ms each, 26 of those 27 seconds), so styles are now read from a table built once, and reading stops at the text limit; at most `MAX_CONCURRENT_PARSES` (default 2) documents are read and indexed at a time, the rest wait and are told to retry (503, `PARSE_WAIT_SECONDS`, default 60) if the wait is long; indexing embeds 100 chunks at a time instead of thousands at once; and the image sets `MALLOC_ARENA_MAX=2` (glibc gave every thread its own arena and kept what big parses freed) and returns freed memory after each document. Result: all 20 uploads stored in 32 s, peak 523 MiB, the health probe never waiting more than 0.1 s.
- Long tables are drawn a page at a time: the requirement table and the story list show 300 rows, then "Showing 300 of 13,800 · Show 300 more · Show all" (focus moves to the first new row). Everything that works on the data still works on every row, drawn or not: search, filters and sorting, select-all (labelled "Select all 13,800 matching", with the usual confirmation for big bulk changes), and the drawer's Next/Prev. Before, a project with thousands of requirements built thousands of rows (and their event handlers) on every filter keystroke. Browser test: `tests/ui/paged_tables.py` (1,200 requirements and 700 stories).
- **A project can now hold 1,000+ BRDs.** The load test (`bigproject` scenario: 1,100 BRDs read into one project, 50,600 requirements) found two ways the app fell over, both fixed:
  - *The pod was killed (OOM, exit 137) and every request took 14-15 s.* Near-duplicate detection compared every pair of alike statements (quadratic time) and stored every duplicate of every requirement (quadratic memory), and ran again on every project summary, list and story estimate. Identical statements are now compared once as a group, at most 8 duplicates are listed per requirement, a comparison budget bounds the work (ordinary sets are still exact; a pathological one, such as thousands of statements from one template, is checked approximately), and the result is cached per project until a requirement changes. With 13,800 requirements: summary 14.4 s -> 0.9 s, requirement list 15 s -> 1.2 s (and 50 MB -> 9 MB), peak memory 313 -> 175 MiB; with 50,600: no crash, 3-5 s per heavy call, 372 MiB peak.
  - *Extraction could not read that many BRDs at all.* One run read every BRD and was capped at 'Max sections per run' (maximum 2,000), so 1,100 BRDs could never be extracted, and re-extracting replaced every reviewed or edited requirement. The run panel now offers **New BRDs only**: it reads the BRDs not read yet, as many as fit the limit, and **adds** to the existing requirements without touching them (numbering continues; a statement repeated in a later BRD gains a source instead of a duplicate). Large intakes take a few runs; the Sources tab marks unread BRDs **New**. **All BRDs: start over** works in batches too: the first batch replaces everything when it is saved (a failed run changes nothing) and the rest become New. API: `documents` = `new`, `reset` or `all` on `POST /runs` and `GET /runs/estimate`. Upgrading marks the documents of projects that already have requirements as read.
- Developer tools: `scripts/run-py-k8s.sh` runs a Python script against the working tree on the cluster (profiling), and the load test reports the app container's restarts and OOM reason.
- **Parallel sections in a run.** A run used to ask the AI about one section at a time, so its length was sections x the provider's latency (46 sections at ~30 s each is ~23 minutes, and 20 requesters on 4 slots would take about 2 hours). Sections are independent, so a run now asks up to **AI requests in parallel per run** (Admin > Generation settings, default 4, 1 to 16) at once, merges the answers back in section order, and stays cancellable; usage counts are exact and a failing section still fails the run naming it. Across all runs the server keeps at most `MAX_RUN_AI_CALLS` (default 8) background AI calls in flight, so provider rate limits are respected however many runs there are. Measured with 20 simultaneous runs against a provider that takes 0.25 s: 61 s -> 31 s overall, 12 s -> 6 s per run, all 920 requests served once; with a 30 s provider the same load drops from about 2 hours to about 1 hour (raise `MAX_RUN_AI_CALLS` if the provider allows). Story generation uses the same mechanism. The database pool default is now 20 connections.
- Fixed a race in run admission found by the new slow-AI load scenario (20 requesters starting at the same instant): every start saw "a free slot", so all 20 runs were labelled "running" although only 4 executed; the waiting ones would also have been failed as "stuck" after 15 minutes (they send no heartbeat). Admission (the one-run-per-project check, the slot count, the queue bound and the insert) is now one atomic step under a database lock, and nobody jumps ahead of a run that is already waiting. Verified: of 20 simultaneous starts exactly 4 are running and 16 queued, never more than 4 running at once, and all 920 AI requests reached the provider exactly once. Load scenario `slowai` (`LLM_LATENCY`, `SLOW_BRDS_EACH`).
- **Run queue.** When every AI run slot is busy, a new run is accepted and queued instead of refused with "try again in a few minutes" (in the load test 53 of 73 start attempts were refused; with a real AI provider a run takes minutes to hours, so retrying by hand is no answer). The page shows "Queued: position N of M", the run starts by itself in order and the page follows, and a waiting run can be removed. The queue is bounded (`MAX_QUEUED_RUNS`, default 50, then HTTP 429), a project still has one run at a time, and waiting runs are failed with a clear message if the server restarts. New metric `fabulist_queued_runs` and alert `FabulistRunQueueBacklog`. Browser test: `tests/ui/run_queue.py`.
- **Load test and the fixes it drove** (`scripts/load-test-k8s.sh`, `tests/load/brd_load.py`; runs on the cluster with the offline AI provider, so no AI spend). Scenarios: 20 requesters each submitting 20 BRDs at the same moment, and one project holding 1,100 BRDs (up to 165 MB of text). Findings and fixes:
  - Uploading a BRD blocked the whole server while it was parsed and stored (health probes waited up to 2.5 s; the pod's probe times out at 1 s). Uploads now run in the worker pool: the same burst leaves the probe at 0.2 s.
  - Listing the documents of a project took 5 s at 1,100 BRDs (a per-document chunk count with no index, quadratic). Now 0.28 s, with an index on `chunks(document_id)`.
  - Exporting a 167 MB project peaked at 796 MiB of the pod's 1 GiB (the archive was built as a dict, a string and a response body at once). It is now streamed: 210 MiB.
  - Starting an extraction that was over the section limit returned 202 and then failed seconds later; it is now refused up front with the same message, and the estimate no longer loads every document into memory.
  - New metrics `fabulist_process_resident_memory_bytes`, `fabulist_process_peak_resident_memory_bytes`, `fabulist_memory_limit_bytes` and an alert `FabulistMemoryNearLimit` (over 85% of the limit for 10 minutes).
  - Known limits, from the measurements: at most 4 AI runs execute at once, and extra requests get HTTP 429 (53 of 73 start attempts in the burst); a single run is capped at 'Max sections per run' (default 200, maximum 2,000), so 20 BRDs of 30 KB need an administrator to raise it, and 1,100 BRDs cannot be extracted in one run at all.

The image running now is clean (Debian 13.7, 0 findings); the script exits 1 on a vulnerable image (checked against an old Python 3.8 image: 61 findings).

- Near-duplicate detection is now exact and fast. The old shortcut (ignore words used by more than 10% of the requirements) found no duplicates at all on a repetitive BRD vocabulary, and its cost grew with the square of the project size, so creating one requirement took 4 ms at 100 items, 76 ms at 1,000 and 153 ms at 1,500 (seeding 3,000 took over 10 minutes). Prefix filtering (AllPairs) gives the exact answer: 3,000 requirements in 15 ms (was 580 ms), 6,000 in 34 ms (was 2.7 s), 12,000 in 94 ms; seeding 3,000 takes 94 s. Filter boxes on the Requirements and Stories tabs wait for typing to pause instead of re-rendering thousands of rows on every keystroke (typing a filter at 3,000 requirements lagged 2.9 s; now the table catches up 0.15 s after the last key).
- Capacity: AI calls made inside a request (Refine, Estimate, Ask the BRDs, provider test) are limited to `MAX_INTERACTIVE_AI_CALLS` (8) in flight; extra requests get an immediate 429 "AI service is busy" instead of holding a web thread. Before, 45 simultaneous Refine clicks against a hung provider froze the whole app, `/healthz` included (measured). New metric `fabulist_ai_busy_total`.
- Capacity: AI runs execute in their own bounded pool (`MAX_CONCURRENT_RUNS`, default 4) instead of the web server's shared worker threads. Before, 40 simultaneous runs made the whole app, `/healthz` included, stop answering (measured); now the 5th gets a clear 429 with `Retry-After` while everything else keeps responding. Runs with no progress for `STALE_RUN_MINUTES` do not hold a slot.
- Stuck AI runs: Cancel now stops the provider retry loop (it used to wait for every remaining retry: 31 s with a 10 s timeout, over 6 min at the default) and the run ends as *cancelled*, not *failed*; a run with no progress for `STALE_RUN_MINUTES` (15) is marked stuck when someone starts another run, so a hung provider can no longer block a project until a restart; a cancelled or stuck run can never overwrite results if its thread finishes later; the run card says when there has been no progress for 3+ minutes. Additive schema change (`runs.updated`), so rolling back is safe.

- Git sync: the clone is pinned to the address that passed the private-network check and no longer follows HTTP redirects (a public host could previously redirect it to an internal service, or change its DNS answer between check and clone); a clone that grows past `MAX_REPO_MB` (500) is stopped; the clone timeout is `REPO_CLONE_TIMEOUT` (60 s, was 120 s, which exceeded the proxy timeout); a blocked redirect says to use the canonical URL.
- Uploads: DOCX/XLSX that would expand beyond `MAX_UNZIPPED_MB` (decompression bombs) or contain thousands of parts are refused before parsing; PDFs over `MAX_PDF_PAGES` are refused and extraction stops once enough text is read; password-protected, scanned and damaged files get a clear message; truncation (long documents, 5,000+ spreadsheet rows, 50+ sheets, long pasted text) is announced in the document text instead of silent.
- Database outages: API calls and `/healthz` return a retryable 503 (JSON message, `Retry-After`) instead of a plain 500; requests wait at most `DB_POOL_TIMEOUT` (10 s, was 30 s) for a connection; the pool validates connections when handing them out, so a database restart no longer fails the next requests (3 of 15 failed before, 0 after), and TCP keepalives detect a partitioned connection.
- Concurrent edits: requirements and stories carry a `rev`; saving from a stale editor returns 409 ("changed by someone else") instead of overwriting, and a bulk status change also makes open editors stale. Clients that send no `rev` behave as before. Additive schema change (`rev` columns with default 1), so rolling back is safe.
- Fix: the product-taxonomy cache ignored invalidation for the first 30 s after a machine boot (a new or edited product class could be missed on a freshly started node).
- Backups: the documented restore command now uses `--clean --if-exists --exit-on-error` (the old one exited 1 with 67 errors on a fresh database); `scripts/restore-drill.sh` verifies dump and restore end to end.
- Fix: going back from a project that was still loading left that project's name in the Projects breadcrumb.
- Project list: from 8 projects a filter bar (name/description, platform) and a sort (newest, name, most left to review) appear; the choice is kept while navigating.
- AI run failures name the section or story group that failed and state that nothing was saved (e.g. "Section 12 of 40 (Returns): provider returned HTTP 503. Nothing was saved; existing results were kept.").
- Tracker push: stops at a time budget (`PUSH_BUDGET_SECONDS`) and reports how many stories remain instead of timing out at the proxy; wrong credentials, permissions or URL stop the push with one actionable message instead of N identical failures; results and errors stay visible in the card and are announced to screen readers; the button says *Publish page* for Confluence.
- Baselines on phones: the table fits, with a one-line contents summary under each name and the Export/Compare actions in reach.
- Accessibility: dialog and side-panel footer buttons now meet WCAG AA contrast (4.43:1 → above 4.5:1). Links inside sentences are underlined (WCAG 1.4.1). Axe-core (WCAG 2.0/2.1 A and AA) is clean on 24 screens, keyboard-only use of the token flow verified.
- Phone layouts: Requirements, Stories (list), Sources, Product taxonomy and Activity tables keep only the essential columns so the content and row actions fit without sideways scrolling; header buttons and attribute rules wrap and stack.
- Admin: all API tokens listed on Users & roles (owner, expiry, last used) with revoke.
- Fix: the Archived view stacked under the normal project list instead of replacing it; on phones the Account and Users tables hide secondary columns so Revoke/Disable stay on screen.
- Personal API tokens (`Authorization: Bearer fab_...`) for scripts and integrations, managed on the new Account page; admin list/revoke API. Additive schema change (`api_tokens`), so rolling back is safe.
- SSO sessions end after 30 minutes of inactivity (`SESSION_IDLE_MINUTES`, `0` disables); activity slides the idle window but never extends the 8 h absolute lifetime. Existing sessions stay valid until their next request refreshes them.
- Projects are archived (read-only, restorable, audit trail kept) instead of deleted; permanent deletion is admin-only and requires an archived project. **Behavior change:** `DELETE /api/projects/{id}` now returns 409 for an active project and 403 for non-admins. Additive schema change (`projects.archived`), so rolling back to the previous image is safe.
